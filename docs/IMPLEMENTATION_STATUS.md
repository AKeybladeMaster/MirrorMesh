# MirrorMesh implementation status

Updated: 2026-10-19. `SOURCE_IMPLEMENTED` means the source slice exists; `CODE_COMPLETE` means all source requirements in that scope are implemented; `BUILD_VERIFIED` requires a successful target build; `AUTOMATED_INTEGRATION_VERIFIED` requires an automated peer-to-peer flow; and `HARDWARE_VERIFIED` requires a physical-device run. These are separate evidence levels. A passing shell check does not establish a media path.

## Functional integration priority

The reference path is Windows x64 sender to the native Android TV receiver. Task 29 provides Linux pairing-runtime assembly source behind an explicit Devices action. Tasks 31–34 provide typed Rust WSS channels, explicit pairing decisions, a QR-pinned sender client, and an Android TV receiver-service API. Rust loopback tests perform signed pairing, validate approval/rejection, and exchange offer/answer control envelopes. Neither platform app invokes these APIs yet. The reference path remains without a connected peer-to-peer media stream: app-integrated signaling, a real WebRTC connection, H.264 encode/decode, Windows capture, Android TV rendering, received-frame screenshots, and end-to-end reconnect/revocation behavior remain unverified.

## Task 02 evidence and limits

The transport core now validates bounded SDP/ICE inputs, orders trickle candidates around remote-description setup, tracks connection and reconnect transitions, converts monotonic capture time to the 90 kHz RTP video timebase, bounds encoded-frame queue bytes/count, requests a keyframe after overflow, and produces a timestamped synthetic I420 color-bar source for an encoder adapter. `WebRtcEnginePort` exposes asynchronous control and metadata events only; its Flutter implementation is pinned in `pubspec.lock` and emits SDP/ICE/connection/track metadata with no capture or media-pixel API.

The Rust tests use synthetic values and do not instantiate libwebrtc, encode H.264, open sockets, authenticate peers, or render video. A real H.264 stream, DTLS-SRTP, signaling, native platform adapters and hardware verification remain open. See [Task 02](../codex/02-transport-spike.md), [ADR-0002](adr/0002-transport-spike.md), and the [transport implementation and deferred-test report](spikes/transport-experiment-blocker.md).

## Task 25: Android explicit-action pairing runtime assembly

The Android Devices page now calls a Kotlin method channel that initializes `AndroidPairingIdentity` and `SqliteTrustedPeers` only after the user's explicit action. JNI retains one process-wide `PairingRuntime`, and returns a stable UUIDv8 derived from the public-key fingerprint. The file-backed store is under app-private `noBackupFilesDir`. The action does not discover/contact another device, approve trust, request capture, or stream. Proposed [ADR-0030](adr/0030-android-pairing-runtime-assembly.md) records the assembly and limits. Twelve adapter tests, three host FFI tests, Flutter analysis and tests, Rust workspace format, strict Clippy, and all-feature workspace tests pass. Android ARM64 compilation is blocked in `dart-sys` by missing NDK clang; no APK or device behavior is verified. The next Android scope is the app pairing flow, followed by consent-gated capture.
