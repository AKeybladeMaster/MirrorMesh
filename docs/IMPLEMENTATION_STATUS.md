# MirrorMesh implementation status

Updated: 2026-10-19. `SOURCE_IMPLEMENTED` means the source slice exists; `CODE_COMPLETE` means all source requirements in that scope are implemented; `BUILD_VERIFIED` requires a successful target build; `AUTOMATED_INTEGRATION_VERIFIED` requires an automated peer-to-peer flow; and `HARDWARE_VERIFIED` requires a physical-device run. These are separate evidence levels. A passing shell check does not establish a media path.

## Functional integration priority

Task 45 adds best-effort, sender-side outbound video statistics to the Windows WebRTC adapter and UI. It distinguishes ICE/WebRTC connection from reported encoded frames and bytes; it does not confirm receiver decode, display, or hardware encoder use. The source is analyzer-checked, but focused Flutter tests and the Windows app build did not complete in this environment.

Task 46 makes the synthetic color-bar target animate inside the MirrorMesh window so the existing selected desktop-capture track has changing content to encode. The pattern is Flutter-rendered content captured by the plugin adapter; it is not a direct native frame feed or WGC. Dart format and analysis pass. The widget test produced no output for 50 seconds and was interrupted (exit 1); the Windows release build produced no output for 30 seconds and was interrupted (exit 1). RTP delivery and TV decode remain unverified.

Task 47 wires the existing `session.start` control message through the Windows sender after WebRTC reports `connected`, then carries it through the approved WSS/JNI channel to the Android TV status listener. It uses only the generic `desktop-capture` label and does not expose a local window ID. Rust, protocol, Windows-target, and direct JDK tests pass. Flutter tests and Windows bundle build stalled without output; Android Gradle/APK build is unavailable. No app-to-app media or decoded frame is verified. See proposed [ADR-0047](adr/0047-windows-session-start-control.md).

Task 48 adds sender-initiated `session.stop` over the approved WSS channel. The Windows controller closes its native capture/peer first, waits briefly for the worker's bounded stop-write acknowledgement, and then cancels pairing; local cleanup continues if signaling fails. Android TV treats remote stop as a normal transition to `STOPPED` and releases receiver resources. Rust workspace/Windows-target checks and direct JDK state tests pass. Flutter and Android SDK builds are unavailable here. This control message does not prove media delivery. See proposed [ADR-0048](adr/0048-windows-tv-session-stop.md).

The reference path is Windows x64 sender to the native Android TV receiver. Task 29 provides Linux pairing-runtime assembly source behind an explicit Devices action. Tasks 31–38 provide typed Rust WSS channels, explicit pairing decisions, a QR-pinned sender client, an Android TV receiver-service API/JNI bridge, cancellable shutdown, native QR approval UI, and TV-side WebRTC signaling handoff source. Task 39 made the sender decision wait pollable and cancellable in the shared Rust client, with loopback control-plane coverage. Task 40 connects Windows UI to QR-pinned pairing and retains the approved WSS channel. Task 41 adds shared v1 offer encoding, a background Windows WSS signaling worker, bounded ICE exchange, and a Flutter WebRTC coordinator. Task 42 rechecks approved pairing and attaches a user-selected plugin desktop track before creating the offer. Task 43 constrains that sender transceiver to locally advertised H.264 codecs before offer creation and fails before capture when none are advertised. Task 44 adds a D-pad gated Android TV screenshot action and bounded one-frame conversion from the receiver. These are source integrations only: the picker/capturer is not verified as Windows Graphics Capture or the OS-owned picker, and the synthetic color-bar card is not a native frame generator. Local H.264 capability does not prove hardware encoder selection. The Windows Flutter bundle, Android TV APK, app-to-app peer exchange, RTP/H.264 delivery, decoded TV frame, and screenshot saving remain unverified. Hardware encoding and persisted revocation remain incomplete; this is not yet a verified mirror stream.

## Task 02 evidence and limits

The transport core now validates bounded SDP/ICE inputs, orders trickle candidates around remote-description setup, tracks connection and reconnect transitions, converts monotonic capture time to the 90 kHz RTP video timebase, bounds encoded-frame queue bytes/count, requests a keyframe after overflow, and produces a timestamped synthetic I420 color-bar source for an encoder adapter. `WebRtcEnginePort` exposes asynchronous control and metadata events only; its Flutter implementation is pinned in `pubspec.lock` and emits SDP/ICE/connection/track metadata with no capture or media-pixel API.

The Rust tests use synthetic values and do not instantiate libwebrtc, encode H.264, open sockets, authenticate peers, or render video. A real H.264 stream, DTLS-SRTP, signaling, native platform adapters and hardware verification remain open.
