# Security, threat model, privacy and lawful interoperability

## Trust boundaries and assets

Assets: captured screen (often highly sensitive), audio, pairing credentials, identity keys, trusted-peer grants, local exported images, sessions and telemetry.

Threat actors: another device on LAN, malicious QR/IP, compromised TV/browser, relay, malicious skill, stolen pairing code, actor with app-store binaries, third-party dependency.

## Local service discovery

The proposed DNS-SD record publishes only a version, persistent device identifier, device roles, QR/TLS requirements, codec capabilities, and the user-selected local display name. SRV/address records provide an unauthenticated endpoint hint; the current adapter accepts only signaling port 8765. The publisher candidate requires an explicit call, accepts caller-supplied RFC1918/link-local IPv4 or ULA/link-local IPv6 addresses, and is not started by the app. Never publish credentials, pairing secrets, IP addresses in TXT, SDP, or media data. The endpoint-preserving candidate port carries resolved IPv4/IPv6 socket addresses, retaining IPv6 interface scope. The application coordinator removes the local ID, endpointless results, and ambiguous duplicate IDs; this filtering does not authenticate a hint. The current parser rejects unknown/missing v1 fields and unusable addresses, but this does not authenticate the sender or make its endpoint safe to trust. Discovery is a selection aid only: verify the QR fingerprint, require explicit approval, and establish authenticated signaling before any capture or stream. The Rust adapter browses the standard mDNS service type; it does not scan arbitrary addresses. Platform multicast permissions and owned-LAN behavior remain unverified.

### Pairing attempt admission

`mm-security::PairingAttemptLimiter` tracks a bounded in-memory budget per source IP. `PairingRuntime::verify_proof_from` and `verify_pair_begin_from` reserve an attempt before proof verification; the raw-frame path reserves before parsing so malformed frames also count. It carries the admitted IP into explicit approval, and successful persistence clears that source's history. The default policy (five attempts, a 60-second partial-history window, a 30-second cooldown, and 1,024 tracked sources) is proposed and awaits security/cross-track review. The future listener must supply the remote socket address and a consistent monotonic clock, keep the runtime alive for its lifetime, and add global connection/message limits. The bounded parser and runtime bridge do not authenticate transport peers. No listener or network behavior is implemented or tested.

### `pair.begin` proof frame

The Rust protocol parser accepts a strict candidate payload: canonical lowercase UUIDs, a 32-character lowercase-hex 128-bit nonce, a 64-character lowercase-hex 32-byte public key, a 128-character lowercase-hex 64-byte signature, and a non-empty unique subset of known grants. The display name is bounded to 80 Unicode scalar values and excludes control characters. Proposed [ADR-0020](adr/0020-pair-begin-wire-encoding-candidate.md) records this encoding and leaves cross-track/security approval open. `verify_pair_begin_from` consumes source admission before parsing, then verifies the canonical proof through the existing identity port; it returns pending approval only. No trust is stored until an owner explicitly approves a grant subset. The parser and candidate schema do not provide TLS, QR fingerprint confirmation on the connection, or a production signaling listener.

`mm-protocol::encode_pair_begin` uses the same payload validation when serializing sender frames. Its caller supplies the signature; the encoder does not sign JSON or establish peer identity. `PairingProof` accessors expose immutable references/copies of the already validated proof data, while its fields remain private. Proposed [ADR-0021](adr/0021-pair-begin-outbound-encoding-candidate.md) records this API; signing and authenticated transport remain separate trust boundaries.

`PairingProof::create_signed` creates the signature through `LocalPairingIdentityPort` and rejects self-pairing before calling the signer. Its caller remains responsible for validating the QR, expiry, receiver fingerprint, and local device-ID binding. Proposed [ADR-0022](adr/0022-sender-proof-creation-candidate.md) records this candidate API; it neither verifies a receiver nor persists trust.

### Trusted-session grant scope

Before it starts a control transport, `TrustedSessionRuntime` loads the peer's active persisted record and checks that the caller-requested `TrustedPeerGrants` are covered by the approved grant set. A denied request returns `GrantNotAuthorized` before transport start. The composed `MirrorMeshRuntime` applies the same gate. The runtime cannot infer local sender/receiver direction; callers must choose the correct operation scope, and capture, annotation, media, and signaling code must enforce their own required grants at those boundaries. Proposed [ADR-0019](adr/0019-trusted-session-grant-scope-candidate.md) records the API candidate. Unit and fake-transport SQLite integration tests cover the denial boundary; no platform, signaling, or real-media path uses it yet.

| Public-exposed local socket | bind LAN only by user intent, firewall prompt, no UPnP and no unauthenticated endpoints | external network negative test |
| Device revoked mid-stream | tear down tracks, keys/tokens, peer state | immediate stop test |
| Capture private notifications | user-select window where possible, obvious sharing indicator; privacy guidance | OS permission flow review |
| Sensitive data in logs | redact IP/private names/tokens/video; debug logs opt-in | grep/log snapshot check |
| Compromised skill | vendor/review pinned SKILL.md, least privileges/no keys | installation checklist |
| Media codec exploitable parser | patched libraries, fuzzing, sandbox OS, no own H.264 bitstream parser | dependency & fuzz gate |
| Artifact compromise | signed release, checksums, SBOM, provenance | independent archive hash |

## Pairing design (MVP)

QR encodes `mirrormesh://pair?v=1&host=<numeric-IP>&port=8765&device=<uuid>&fp=<64-lowercase-hex-SHA256-public-key-fingerprint>&nonce=<32-lowercase-hex-digits>&expires=<unix-seconds>`; ensure QR is displayed in owner-controlled receiver UI. Never transmit credentials to an unknown URL from arbitrary QR text. `parse_pairing_qr` enforces this narrow shape, approved numeric endpoints, canonical fields, and a future expiry no more than 120 seconds away. CORE has a bounded helper that fills 128-bit nonces from the OS random source and permits one use before a 120-second local monotonic deadline. The QR Unix expiry is a separate wall-clock check. ADR-0004 defines a 32-byte SHA-256 fingerprint over the canonical presented public-key encoding. The proposed [ADR-0007](adr/0007-ed25519-identity-candidate.md) specifies raw Ed25519 public-key bytes (32 bytes), signatures (64 bytes), and hashing those raw key bytes for the fingerprint. A stateless verifier candidate is implemented in `mm-adapter-identity` and passes RFC 8032, malformed-key, and invalid-signature tests; its `verify_strict` acceptance profile remains subject to cross-track/security review. The domain record validates bounded public-key bytes, scoped grants, and timestamps, and enforces one-way revocation; `TrustedPeerPort` defines the persistence boundary. `mm-application::PairingCoordinator` composes the invitation parser, nonce registry, `PairingIdentityPort`, and trusted-peer storage contract. It verifies the domain-separated sender proof, then creates a pending approval; only explicit approval of a requested-grant subset persists trust. The coordinator unit tests use fakes; three `mm-runtime` integration tests now exercise the flow with the real Ed25519 verifier and SQLite trusted-peer adapter, confirming that trust is saved only after explicit approval and modified signatures do not persist. One test uses proposed [ADR-0018](adr/0018-pairing-session-runtime-composition-candidate.md)'s `MirrorMeshRuntime` facade to compose pairing and session lifecycle over one identity/store; its transport remains fake-backed. `mm-store::SqliteTrustedPeers` stores public peer data only. Proposed [ADR-0009](adr/0009-windows-identity-key-storage.md) describes a Windows Credential Manager candidate; proposed [ADR-0011](adr/0011-linux-identity-key-storage.md) describes a Linux Secret Service candidate. Both keep the private seed out of SQLite and fail closed when storage is unavailable, but neither has accessed the real OS key store or been assembled into platform startup. Secret Service item attributes contain application/purpose metadata, not key material; same-user callers may still request the exportable seed from the active service. Android Keystore and iOS Keychain candidates, QR UI, and authenticated listener/TLS pinning remain open. `mm-security::PairingAttemptLimiter` is a proposed in-memory admission candidate with five attempts per source, a 60-second partial-history expiry, a 30-second cooldown, and a 1,024-source cap; it awaits security review and listener integration in [ADR-0015](adr/0015-pairing-attempt-limiter-candidate.md). The signing proof contract is recorded in proposed [ADR-0006](adr/0006-pairing-coordinator-proof-contract.md). For first-time manual PIN without QR, implement audited PAKE; until then fallback requires visual fingerprint comparison and a user-approved local connection (no silent TOFU).

The current manual-address parser accepts numeric IPv4 and bracketed IPv6 only, and only when the caller supplies the port in its explicitly user-approved list. It never resolves a hostname. Do not add hostname-based manual connections until the network adapter pins a single resolution result for the connection, rejects redirects, and verifies the expected peer fingerprint; the parser alone does not authenticate or connect to a peer.

**Cloud TV pairing (optional):** a narrowly scoped HTTPS broker maps short-lived room codes to signaling messages, authenticates both ends, and never handles video plaintext. The TV browser uses HTTPS origin; ICE tries direct local UDP. TURN is optional and relay bandwidth incurs costs. Explain cloud dependence in UI and privacy policy.

## External data / user controls

Default: offline/local, no analytics, no auto-upload and no crash dumps unless opted in. Private identity candidates use Windows Credential Manager and Linux Secret Service; Android Keystore and iOS Keychain remain planned. Linux currently fails closed if Secret Service, its session bus, authorization, or a safe runtime lock location is unavailable; no passphrase fallback is implemented. No keys in `trusted_peers` aside from public keys.

Exports user initiated, locally saved, and deletable. UI must show **active capture indicator**, session recipient, permission state and immediate Stop/Disconnect. Recording/casting remote screens requires permission from content owners; protected/DRM windows may be blanked by OS—do not circumvent.

## REA and open-source legal boundary

- Verify law applicable to binary examination/contract, purpose, interoperability exceptions and redistribution. No universal assurance that decompiling Store packages is permitted.
- No bypass of signing, encryption, DRM, paywalls, license checks or access controls.
- No copying binaries, decompiled source, proprietary assets or trademarks into product code/README.
- Keep independent team/code and evidence-only summaries; use public protocol specifications and official APIs.
- Check libraries for patent, redistribution, GPL/LGPL/Apache obligations including dynamically linked GStreamer/codec plugins.
- Treat AirPlay/Google Cast/Miracast brand/protocol claims separately from generic WebRTC. Do not claim official compatibility without validation.
- Choose repository license only after SBOM license review.
