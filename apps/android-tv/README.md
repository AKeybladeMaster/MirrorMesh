# MirrorMesh Android TV receiver shell

This is a separate native Android TV application target. It declares the Leanback launcher, touchscreen-free navigation, app icon, and TV banner. The main activity lists active local IPv4 addresses, starts the Rust-owned pairing listener, displays a short-lived one-time QR invitation, waits for a verified sender request off the UI thread, and presents the sender fingerprint and requested grants. All permission boxes begin unchecked; approval and rejection require separate remote-control actions. A refresh action cancels the current idle wait and issues a fresh invitation; rejection and channel close also refresh the one-time code. It also contains a native receive-only WebRTC adapter and fullscreen `SurfaceViewRenderer` activity. The adapter accepts only an approved signaling channel, bounds SDP and ICE inputs, configures a receive-only transceiver with H.264-only codec preferences, and uses `HardwareVideoDecoderFactory` without a software decoder fallback.

The approved pairing channel polls Rust-validated `session.offer`, `session.ice`, `session.start`, and `session.stop` messages, sends Rust-encoded H.264 answers and local ICE, and opens the fullscreen WebRTC receiver on the first offer. Task 47 validates the bounded start source label against the active session and reports that the sender says capture started; this is not a decoded-frame confirmation. Task 48 treats sender stop as a normal `STOPPED` transition and releases the TV peer and renderer. ICE arriving before renderer setup is buffered with a fixed limit. Windows sender source now covers approved pairing, offer/ICE exchange, user-selected desktop-track attachment, H.264-only codec preferences, a post-connect session-start notice, and explicit disconnect. No Windows app-to-TV WebRTC run has been verified. Task 44 adds a user-triggered screenshot action that copies only the next decoded frame and saves it with MediaStore on Android 10+ or to app-specific storage on older versions. The native screenshot path and synthetic media sender are not build- or integration-verified, so a functioning mirroring session is not yet verified. The app requests only the ordinary `INTERNET` permission; cleartext traffic is disabled and no local screen, camera, or microphone capture is requested. ZXing Core 3.5.4 (Apache-2.0) encodes the invitation QR. Native Android TV is the primary TV path; the browser receiver remains a compatibility fallback.

## Build

Install JDK 17 or newer, Android SDK platform 37, Build Tools 36.0.0 or newer, NDK 28.2.13676358, Rust 1.99.1 with the `aarch64-linux-android` target, and Gradle 9.6.0. From this directory run `gradle :app:assembleDebug`. Gradle builds and packages the shared `mm_ffi` Rust library for ARM64. The output is `app/build/outputs/apk/debug/app-debug.apk`. An emulator build is only a compile/UI smoke check; it does not prove hardware decoding or a real TV session. The native JNI pairing bridge is wired to the activity; the APK has not been built on this workstation.

GitHub Actions runs the Java state checks separately from an Ubuntu native APK build. The build job installs Android platform 37 and Build Tools 36.0.0, assembles the debug APK, and prints its SHA-256 digest. It does not publish or sign the APK.

## Local behavior checks

From the repository root run:

```powershell
powershell.exe -File .\apps\android-tv\scripts\test-demo-state.ps1
powershell.exe -File .\apps\android-tv\scripts\verify-shell.ps1
```

The JDK-only tests cover explicit pairing state, bounded H.264 SDP selection, receiver lifecycle including sender-driven `STOPPED`, bounded I420-to-NV21 screenshot conversion, and the Task 47 source-label validator. XML/source checks verify bridge wiring, QR dependency, explicit grant selection, approved signaling, INTERNET-only permission, hardware decode policy, the screenshot action, and normal remote-stop handling. The Android app has no build evidence on this workstation because Gradle and the Android SDK/NDK are unavailable. Rust protocol and loopback tests cover bounded control polling and validated answer/ICE/start/stop envelopes, but they do not instantiate Android WebRTC. No actual QR scan, sender connection, screenshot write, or media playback is claimed. Final hardware testing must install the APK on an Android TV, pair to a Windows sender, explicitly approve, receive H.264, verify fullscreen hardware decode and screenshot saving, and exercise disconnect, reconnect, rejection, and revocation. Emulator compilation is build evidence only, not TV hardware evidence.
