# TASK 03 — mDNS discovery, QR trust and authenticated signaling

**Skills:** TDD, security-review (after audit), rust-best-practices, requesting-code-review

**Scope:** Shared CORE pairing runs in parallel with platform adapters; Android TV native `Accept/Reject` is the primary TV onboarding UI, web QR fallback is separate and secure-origin dependent. Cross-agent protocol changes need CORE review.

## Current progress (2026-10-18)

The shared CORE contract now has a bounded manual endpoint parser, strict QR parser, OS-random one-time nonce registry, validated trusted-peer record and storage/identity ports, plus a fake-backed `mm-application::PairingCoordinator`. It creates invitations, validates the domain-separated proof, enforces one-time nonce use and explicit grant-subset approval, and persists only after approval. See [ADR-0004](../docs/adr/0004-trusted-peer-records.md), [ADR-0005](../docs/adr/0005-sqlite-trusted-peer-store.md), [ADR-0006](../docs/adr/0006-pairing-coordinator-proof-contract.md), proposed [ADR-0007](../docs/adr/0007-ed25519-identity-candidate.md), proposed [ADR-0010](../docs/adr/0010-pairing-runtime-composition.md), and proposed [ADR-0011](../docs/adr/0011-linux-identity-key-storage.md). The candidate encoding is Ed25519 with 32-byte raw public keys, 64-byte signatures, and SHA-256 fingerprints over the raw public-key bytes. A stateless `mm-adapter-identity` verifier candidate pins `ed25519-dalek 3.0.0`, `curve25519-dalek 5.0.0`, and `sha2 0.11.0`; six RFC 8032 and negative-input tests pass. Canonical-key and low-order checks plus `verify_strict` still need cross-track/security approval. The versioned SQLite trusted-peer adapter in `mm-store` passes ten tests. A generic `mm-runtime::PairingRuntime` composes the coordinator with local identity, trusted-peer storage, and per-source attempt admission before proof verification; eleven fake-backed unit tests pass, and three integration tests exercise the real Ed25519 verifier and SQLite store through the consent-gated flow. Concrete OS adapter assembly into platform app startup remains open. The Windows Credential Manager identity candidate passes ten fake-store tests, including canonical proof-message rejection, rotation, deletion, and storage-failure cases. It compiles the Win32 calls but has not accessed a real credential. The Linux Secret Service identity candidate passes eight fake-store tests and compiles for the GNU Linux target on Rust 1.99.1 and 1.85; it has not accessed D-Bus or a user's keyring. `mm-security::PairingAttemptLimiter` atomically reserves attempts, normalizes IPv4-mapped IPv6, bounds tracked sources, and clears a source after approved pairing. Its eight tests include 20 admissions across cooldowns and concurrent source admission; the default policy is pending security review. No network listener uses the runtime yet. Remaining Task 03 work includes cross-track/security approval of the verifier profile, shared ports, and admission policy; concrete platform app assembly; live keyring validation plus Android/iOS protected key storage; mDNS app integration; authenticated TLS/WSS signaling and listener integration; platform QR/approval UIs; direction-correct grant enforcement at signaling/media/capture/annotation boundaries and closure of OS capture/codec resources on revoke; and owned-LAN/device verification. Protocol v1 remains a candidate pending cross-track and security review.

The endpoint-preserving mDNS application boundary is now present as a proposed CORE candidate: `DiscoveryCandidatesPort` retains socket endpoints (including IPv6 interface scope), and `mm-application::DiscoveryCoordinator` removes the local device, endpointless results, and ambiguous duplicate IDs without establishing trust. See proposed [ADR-0014](../docs/adr/0014-discovery-candidate-application-boundary.md). App startup, FFI/UI selection, platform identity assembly, and LAN behavior remain open.

## Deliverables and detailed steps

### Shared mDNS discovery candidate (2026-10-18)

`crates/mm-adapter-discovery/` now contains a `DiscoveryPort` candidate backed by pinned `mdns-sd 0.21.5`. It browses `_mirrormesh._tcp.local.` for at most two seconds, parses the proposed strict TXT v1 fields, filters unusable endpoints, and returns device hints and resolved addresses. Eleven parser tests pass on Rust 1.99.1 and Rust 1.85 without opening sockets. This is not yet assembled into app startup and did not exercise multicast or an owned LAN. Proposed [ADR-0012](../docs/adr/0012-mdns-discovery-candidate.md) records the dependency and schema; its cross-track/security review remains pending. The upstream compatibility statement covers Windows, Linux, and macOS; Android and iOS still need native discovery and permission adapters.

### Shared mDNS service publisher candidate (2026-10-18)

`MdnsServicePublisher` builds the same strict v1 service record from a caller-supplied `Device`, `.local.` hostname, and explicit LAN addresses. It accepts only private/link-local IPv4 or unique-local/link-local IPv6, caps addresses at 16, fixes signaling to port 8765, and supports explicit stop with a bounded daemon shutdown wait. Proposed [ADR-0013](../docs/adr/0013-mdns-service-publication-candidate.md) records the API and limits. Eight new tests cover record construction, metadata and address bounds, invalid input before daemon creation, and idempotent inactive stop without opening sockets. The app does not yet have stable local identity/runtime assembly, so the publisher is not started from its UI or at app startup.

### Endpoint-preserving discovery application candidate (2026-10-18)

`mm-ports` now exposes the additive `DiscoveryCandidatesPort` contract and `DiscoveryCandidate` value; the existing device-only `DiscoveryPort` stays available. `mm-adapter-discovery` converts validated mDNS results to sorted/deduplicated `SocketAddr` values and carries IPv6 interface scope. The application coordinator removes the local device ID, empty endpoint sets, and all duplicate claimed IDs from one scan; it returns remaining candidates in stable ID order and does not verify keys or save trust. Three application tests cover filtering/order, ambiguous/endpointless hints, and error/stop behavior; two adapter tests cover endpoint conversion and IPv6 scope preservation. Proposed [ADR-0014](../docs/adr/0014-discovery-candidate-application-boundary.md) records the contract. No socket, multicast, or UI test ran; cross-track/security review is pending.

### Pairing attempt admission candidate (2026-10-18)

`mm-security::PairingAttemptLimiter` reserves a source-IP attempt atomically before proof verification. `mm-runtime::PairingRuntime::verify_proof_from` now requires the source address, calls the limiter before the verifier, and returns a pending approval bound to that source; explicit approval clears its history. The proposed default admits five attempts, starts a 30-second cooldown at the threshold, expires partial attempt history after 60 seconds, and caps tracked source addresses at 1,024; IPv4-mapped IPv6 shares the IPv4 budget. Eight limiter tests cover cooldown boundaries, concurrent admission, address normalization/isolation, success reset, capacity fail-closed behavior, policy validation, deadline overflow, and 20 attempt admissions across cooldowns; eleven runtime tests cover source admission and approval reset. Proposed [ADR-0015](../docs/adr/0015-pairing-attempt-limiter-candidate.md) and [ADR-0016](../docs/adr/0016-pairing-runtime-admission-candidate.md) record the candidate policy and composition. No signaling listener, socket, or network test exists, and cross-track/security review remains pending.

### Trusted-session revocation runtime candidate (2026-10-18)

`mm-runtime::TrustedSessionRuntime` checks that the trusted-peer store marks a peer active before starting a control transport. Revocation blocks starts in memory before attempting persistence, then closes every tracked session owned by that peer even if storage fails; close failures stay tracked for retry, while unrelated peers continue. Five fake-backed tests cover untrusted starts, peer-scoped revoke, reconnect denial, persistence failure, failed-start cleanup, and retry after close failure. If persistence fails, local sessions close and new starts are blocked until this runtime ends, but the peer may still be active after process restart. Proposed [ADR-0017](../docs/adr/0017-trusted-session-revocation-runtime-candidate.md) records the lifecycle. No platform app or signaling listener uses this runtime, and closing `TransportPort` does not by itself stop unintegrated OS capture or codec resources. Cross-track/security review and network/device verification remain pending.

The file-backed SQLite integration in `crates/mm-runtime/tests/trusted_session_revocation_sqlite.rs` verifies per-peer closure, persists revocation across database close/reopen, and checks that a newly constructed runtime blocks the revoked peer while allowing another. This remains a local adapter test with a fake transport, not a process, network, or device test.

### Pairing and trusted-session runtime composition candidate (2026-10-18)

`mm-runtime::MirrorMeshRuntime` constructs `PairingRuntime` and `TrustedSessionRuntime` with one identity, one `TrustedPeerPort`, and one transport. The real-verifier/SQLite integration harness now exercises invitation creation, admitted proof verification, explicit approval, trusted control-transport start, persisted revoke/close, and start denial after runtime recreation. Proposed [ADR-0018](../docs/adr/0018-pairing-session-runtime-composition-candidate.md) records the public facade; cross-track/security review remains pending. No protocol, listener, session offer, capture grant, media, app startup, or platform path is included.

### Trusted-session grant scope gate (2026-10-18)

`TrustedSessionRuntime::start_session` and `MirrorMeshRuntime::start_session` now require the caller's requested `TrustedPeerGrants`. They read the persisted peer, require it to be active, and reject a scope outside the approved grant set before `TransportPort::start`. A fake-backed unit test and the real-verifier/SQLite composition test verify that a denied send scope leaves transport unopened while the approved view scope starts. Proposed [ADR-0019](../docs/adr/0019-trusted-session-grant-scope-candidate.md) records this public API/security candidate. The current API does not infer local sender/receiver direction; future signaling, media, capture, and annotation paths must choose and enforce the operation-specific scope. No network, platform, device, or benchmark test ran.

### Strict `pair.begin` runtime bridge (2026-10-19)

`crates/mm-protocol` now validates the candidate pairing payload and `tests/protocol-golden/pair-begin-v1.json` records its exact field names and encodings. `PairingRuntime::verify_pair_begin_from` reserves the source budget before parsing, builds the existing `PairingProof`, and verifies through the existing coordinator; `MirrorMeshRuntime` exposes the same entry point. Six pairing/SQLite integration tests cover typed proofs and raw frames, including approval-only persistence, tampered signatures, and malformed-frame throttling. Proposed [ADR-0020](../docs/adr/0020-pair-begin-wire-encoding-candidate.md) records the wire candidate. Rust 1.99.1 workspace gates pass, focused protocol/runtime tests and GNU/Linux compilation pass on Rust 1.85, and no listener, TLS, platform app, network, or device was exercised. The encoding and Ed25519 profile still need security and cross-track approval before v1 freeze.

### Outbound `pair.begin` encoder (2026-10-19)

`PairingProof` now exposes read-only accessors for its validated fields, and `mm-protocol::encode_pair_begin` emits the same sessionless v1 schema used by the inbound parser. A private serialization view keeps callers on the shared validator. The real-signature SQLite integration now encodes its frame with this API before receiver verification. Thirteen protocol tests pass, including encode/parse round-trip, zero-sequence rejection, and malformed-payload rejection. Proposed [ADR-0021](../docs/adr/0021-pair-begin-outbound-encoding-candidate.md) records the API. It does not perform signing, TLS, or network I/O, and the schema remains pending review.

### Sender-side proof creation (2026-10-19)

`PairingProof::create_signed` obtains the local public key through `LocalPairingIdentityPort`, validates the candidate proof fields, signs the canonical application message, and returns a validated proof. It rejects self-pairing before signer access and reports signer or validation errors without returning a partial proof. Fake-backed application tests cover canonical signer input, self-pair rejection, and signer failure. The real-verifier/SQLite integration now creates the proof through this helper, maps it through the shared outbound encoder, then exercises receiver verification. Proposed [ADR-0022](../docs/adr/0022-sender-proof-creation-candidate.md) records the candidate API. Callers must still validate QR expiry and receiver fingerprint; no TLS, listener, or persistence behavior was added.
