## Pairing bootstrap candidate (Task 28, 2026-10-19)

Task 41 adds a worker-owned shared-v1 offer/ICE bridge and a Dart coordinator around the pinned WebRTC engine; proposed [ADR-0042](../docs/adr/0042-windows-sender-session-signaling.md) records its API. Task 43 restricts the sender transceiver to locally advertised H.264 codecs before offer creation; proposed [ADR-0044](../docs/adr/0044-windows-h264-codec-preference.md) records the codec contract. Task 45 adds best-effort outbound video diagnostics through the pinned WebRTC sender stats API. Task 46 animates the existing color-bar pattern inside the MirrorMesh Flutter window. Selecting that window sends changing desktop content through the pinned plugin capture and the already H.264-constrained sender track. The pattern is not a direct native frame feed, WGC capture, hardware-encoder proof, or evidence that a frame reached the TV. Dart format and analysis pass; the focused widget test and Windows build both stalled without output and were interrupted, so neither is verified.

Task 47 wires the existing `session.start` message through the Windows C ABI and method channel. Dart queues it once after the WebRTC peer reports `connected` and pending local ICE writes drain. It sends only the generic `desktop-capture` label. Android TV validates the bounded notice and shows that the sender reported capture start; no frame receipt or decode is implied. Rust tests, Windows-target tests/Clippy, DLL linking/export inspection, Dart analysis/format, and direct TV JDK tests pass. The focused Flutter tests and Windows release build stalled without output; Android Gradle/APK is unavailable. Proposed [ADR-0047](../docs/adr/0047-windows-session-start-control.md) requires cross-track review because shared protocol/FFI surfaces changed.

Task 48 sends the existing `session.stop` message through the Windows worker before the approved pairing channel closes. The controller releases the local capture and WebRTC peer first, then sends a bounded generic reason and cancels pairing; failed signaling does not block local cleanup. Rust tests and the two-process WSS stop-sequence test pass. Flutter/Dart and current C++ runner builds are unverified because their SDK tools are unavailable. Proposed [ADR-0048](../docs/adr/0048-windows-tv-session-stop.md) records the public API change. No app-to-TV media is verified.

Task 50 separates `transportConnected` from sender-reported `streaming`. The Windows controller sends the existing `session.start` notice only after WebRTC reports a connected peer and outbound statistics report at least one encoded video frame. It waits up to 15 seconds after connection for that first frame, then closes capture/peer and the approved pairing channel on timeout. This is a local sender-side encoding gate; it does not prove RTP delivery or a TV-decoded frame. The tests cover delayed first-frame reporting and timeout cleanup, but Flutter/Dart are unavailable on this workstation, so formatting, analysis, tests, and the Windows app build are not verified. The Flutter CI workflow now runs on `task_*` pushes as well as `main`.

Task 51 adds `reconnecting` for an established peer that reports a temporary disconnect. The controller keeps the same approved capture/peer for a 10-second grace period and lets libwebrtc recover; it does not recreate capture or queue a second `session.start`. Recovery restores transport-only or sender-reported encoding state. Timeout closes capture/peer, attempts the existing `session.stop`, cancels pairing, and reports failure. Mock-backed tests cover recovery and timeout ordering, but Flutter/Dart are unavailable so formatting, analysis, and tests remain unverified. Proposed [ADR-0051](../docs/adr/0051-windows-peer-reconnect.md) records the public state contract. This does not verify network reconnection or TV frame continuity.
